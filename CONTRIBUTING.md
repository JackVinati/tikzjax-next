# Contributing

Bug reports, fixes and package requests are all welcome. This file is what you need to build the
plugin, check a change the way CI will, and get it merged. The design record behind it is
`internal/DECISIONS.md`, which wins wherever it disagrees with the older `internal/DESIGN.md`.

## Building

You need Node `^22.13.0`, `^24` or `>=26` (what ESLint 10 and Vitest 5 accept), and nothing else.

```sh
npm ci
npm run build          # main.js and styles.css
```

That is the whole thing. The compressed TeX engine — 8.5 MiB of WebAssembly, a gzipped core dump,
247 TeX files and 152 fonts — is committed under `engine-build/out/`, so a fresh clone builds in
seconds with no Docker, and the build is reproducible: the same commit gives the same `main.js` and
`styles.css` on any machine. Do not commit `main.js`; `styles.css` is generated by the build and
committed, so commit it when the build changes it.

To develop against a real vault, point the build at it and it will copy the files on every rebuild:

```sh
OBSIDIAN_PLUGIN_DIR="$HOME/vaults/dev/.obsidian/plugins/tikzjax-next" npm run dev
```

It also drops a `.hotreload` marker in that folder, so with
[pjeby/hot-reload](https://github.com/pjeby/hot-reload) installed in the vault the plugin reloads
about a second after a rebuild, without touching Obsidian.

## Checking a change

CI runs these on every push and pull request, and the release runs the same file on the tagged
commit before it publishes anything. All of them work offline and without Docker:

```sh
npm run format:check   # Prettier; `npx prettier --write <file>` on the files you changed
npm run lint           # oxlint, fast
npm run lint:store     # the community store's rules (ESLint + eslint-plugin-obsidianmd)
npm run typecheck      # TypeScript 7
npm run typecheck:legacy  # TypeScript 5, the one the store's review reads the code with
npm test               # unit tests; `npm run test:coverage` adds coverage and its floors
npm run smoke          # every fixture through the engine, headless
npm run verify:golden  # every fixture against the output recorded in test/fixtures/golden
npm run verify:worker  # the exact worker string that goes into main.js
npm run verify:worker -- --legacy  # the same, without DecompressionStream and Uint8Array.fromBase64
npm run verify:reset   # the engine's memory, reset between runs, against a new one, byte for byte
npm run build
npm run scan:native -- --check   # about a minute
```

`lint:store` reports a set of known warnings: sentence-case false positives on names like TikZ and
TeX, deprecations that the 1.7.2 floor requires (`setWarning`, `display`), and the declarative
settings API the floor rules out. A change should add none.

## Rules a change has to keep

Most of these are enforced by a check, and the check says what it found. They are here so the
reason is not a surprise.

- **No network.** The plugin makes no network request, ever: the engine runs offline and that is a
  promise, not a default. CI greps `src/` and `engine-src/` for `fetch`, `XMLHttpRequest`,
  `sendBeacon` and `WebSocket`.
- **The store's rules.** No `innerHTML`, `outerHTML` or `insertAdjacentHTML`; build DOM nodes. No
  assignments to `element.style`; use `setCssStyles` or a CSS class. Register listeners, intervals
  and observers through the plugin (`registerEvent`, `registerDomEvent`, `register`) so they are
  torn down on unload. Settings text in sentence case.
- **No `String.prototype.replaceAll`**, and nothing on the hot path that a community plugin could
  have monkey-patched: one did, and silently broke rendering in the plugin this forks from (#48).
  Use `split`/`join`. A lint rule enforces it.
- **Obsidian 1.7.2.** `minAppVersion` is set by the API the plugin calls, not the one it is written
  against, because Obsidian on iOS trails the desktop. `lint:store` compares every call with the
  floor (`no-unsupported-api`); a newer API needs a reason good enough to move it.
- **iOS Safari.** `npm run build` refuses a bundle containing syntax older Safari cannot parse: no
  regex lookbehind, no static blocks, no `.at(-1)`, `Object.hasOwn`, `findLast`, `toSorted`,
  `groupBy`, `Promise.withResolvers`, `structuredClone` or `RegExp.escape`. A syntax error there
  does not fail one feature; the whole plugin fails to load.
- **Reproducible output.** Nothing in the build may depend on the time, on randomness or on a path
  on your machine. The community store rebuilds releases and compares bytes.
- **The cache key is a promise.** Anything that changes the bytes a diagram renders to has to change
  its cache key, or users keep seeing the old render. `internal/DESIGN.md` §6 says what goes in it,
  and `internal/DECISIONS.md` D20 what changed in 0.2.1. A change to a stage in `src/svg/` that can
  write a different template bumps `PIPELINE_REVISION` in `src/cache/key.ts`, once per release;
  `test/pipeline-revision.test.ts` fails on any edit there until you have decided, and records the
  stage modules' fingerprint.
- **The engine's output has a revision of its own.** The key holds `OUTPUT_REVISION`
  (`src/cache/key.ts`), not the engine's build, so a faster engine that draws the same recompiles
  nothing. Move it whenever what TeX or the converter writes can change: when a fixture's golden
  output changes (`test/output-revision.test.ts` fails until you do), and by hand whenever the
  CHANGELOG says diagrams draw differently, also when no fixture shows it — a package bundled that
  was missing, a fixed TeX file, a converter fix for a glyph no fixture uses. Then
  `node scripts/output-revision.mjs --record`. A new fixture is recorded without a bump. A block
  whose input has a character the Unicode bridge draws has one more field in its key
  (`internal/DECISIONS.md` D26), which moved those keys in 0.2.1; a later change to what the bridge
  draws moves `OUTPUT_REVISION` like any other.
- **Two TypeScripts.** TypeScript 7 typechecks; TypeScript 5.9.3 runs the store lint and the
  `typecheck:legacy` cross-check, because the store's review reads the code through TypeScript 5.
  `internal/DECISIONS.md` D5 says why. Both packages ship a `tsc`, so scripts name theirs by path.

## Changing the engine

The worker in `engine-src/` is ordinary TypeScript, bundled by the normal build: changing it needs no
Docker. ENGINE_ID is the sha256 of the minified worker, so a change that reaches it — code, a TeX
file, a dependency the worker bundles, an esbuild that minifies differently, but not a comment —
moves the id. That no longer recompiles anything by itself: `test/engine-id.test.ts` fails until the
new worker is recorded with `node scripts/output-revision.mjs --record`, and before you record it,
decide whether any diagram can draw differently. If one can, move `OUTPUT_REVISION` too, which
recompiles every user's cached diagrams once (say so in the commit message and the CHANGELOG). The
list of characters the engine typesets is recorded against the id, so run `npm run scan:native` and
commit `src/source/native-unicode.ts` with the change.

Rebuilding the engine itself — after a change under `engine-build/` — needs Docker and about
fifteen minutes:

```sh
npm run engine:image   # container with a pinned TeX Live and the web2js toolchain
npm run engine:build   # tex.wasm, core.dump, tex_files, fonts -> engine-build/out/
npm run scan:native    # which characters that engine typesets -> src/source/native-unicode.ts
```

TeX itself is `tex.web` with change files applied by tie: web2js's own, and then ours, in
`engine-build/changes`, which the build appends to web2js's list (`internal/DECISIONS.md` D16). A
change to what TeX does goes there, as one more change file, and the build stops if tie cannot apply
it. The image carries a copy, so rebuild the image after editing one.

web2js compiles TeX to WebAssembly with three of its compiler's files replaced by ours, in
`engine-build/web2js-codegen`, which keep a procedure's local variables in WebAssembly locals
instead of in memory (`internal/DECISIONS.md` D27). The build checks each of web2js's files against
the sha256 of the one ours was written against, and stops if one has moved: moving the web2js pin
means carrying its change into ours and updating the sum. binaryen 132's `wasm-opt` then optimises
the engine. Values in WebAssembly locals take room on the JavaScript engine's own stack, which bounds
how deep TeX can nest, so `verify:worker` requires a floor of nested `\number` to render and prints
how deep they go (D28). Our files also have the engine mark how far a run took `pool_ptr`, `str_ptr`
and the shadow stack, which TeX itself does not record: the worker keeps one memory and, before each
run, writes the core dump back over only what the run before can have written, found from those
marks, TeX's own counters and `engine-build/out/memory-layout.json` (D31). `verify:reset` holds that
to a new memory, byte for byte, before every run of every fixture in five orders; a change to the
engine, to `engine-src/reset.ts` or to what the host writes into TeX's memory has to keep it passing.

Building the image is the only step that touches the network: it pins the upstream sources by commit
(`engine-build/pins.env`), the font archive by SHA-256 and binaryen by the integrity npm publishes
for it, then bakes them in, so `engine:build` runs entirely offline. The Engine workflow rebuilds
the engine and diffs it against what is committed, so commit `engine-build/out/` and
`src/source/native-unicode.ts` in the same commit as the change that produced them.

To debug on an iPhone or iPad, where there are no devtools: on the device, Settings → Apps → Safari
→ Advanced → Web Inspector; connect it to a Mac by cable; then in Safari on the Mac, Develop → the
device → the Obsidian window. That gives you the console and the debugger against the running
plugin.

## Commits and pull requests

One logical change per commit. The title says, in plain English, what changes for the user or the
code; the body says what was wrong, why, and what the change does about it. `git log` has plenty of
examples. A bug fix comes with a test that fails without it, unless it genuinely cannot have one,
and then the message says why.

Add a line for anything a user would notice to the newest section of `CHANGELOG.md`.

## Releases

Maintainers only, and in this order, because the store reads `manifest.json` from main and looks for
a release with that version:

1. One commit bumps `version` in `manifest.json` and `package.json`, adds the version to
   `versions.json` with the `minAppVersion` it needs, dates its `CHANGELOG.md` section
   (`## 0.1.5 — 2026-10-20`), and carries the `styles.css` that `npm run build` writes after the
   bump: its banner names the version, and `test/banner.test.ts` fails until it is rebuilt.
2. `git tag -a <version>` on that commit, and push **the tag first**. The release workflow runs CI's
   whole gate on it, checks the tag against the manifest and `versions.json`, builds, attests the
   assets and publishes, with the changelog section at the top of the notes.
3. Push main once the release exists.

Every version is re-reviewed by the community store, so small changes ride along with the next
planned release rather than becoming one each.
